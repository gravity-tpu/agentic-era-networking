## 4. Experiment definitions

### 4.1 Rate ladder

`ladder` holds a fixed offered UDP packet rate for a step (45 s for the 600-byte ladders in rounds 1 and 2; 30 s for the 64-byte, 1470-byte and layout ladders), then raises it. Rates for 600-byte ladders: 500, 1000, 2000, 4000, 6000, 8000, 10000, 12000, 15000 pps. Depths: 0, 16, 32, 64, 126 quarantine rules (two forwarding rules are always present). The table is installed and verified by OpenFlow readback before the first step. A climb stops after two saturated steps (forwarded below 90% of offered) or a step with a session loss; after a loss the harness waits for the redial, restores the table and pauses 6 s. After each step it waits up to 20 s for an echo reply, so a stall that surfaces after the load ends is still caught.

Payload sizes: 572 bytes (a 600-byte IP packet), 64 and 1470 bytes. Layouts: `base`, `fwdfirst`, `fwdabove`, `fwdinstall`, `net16`, `distinct` (section 2 of the whitepaper).

### 4.2 Working-window simulation

`workday` runs 12 windows of 300 s. Each window starts by flushing the quarantine rules (selective delete) and reinstalling nothing but the two forwarding rules, then adds rules at even intervals up to the profile maximum (low 8, typical 24, worst 126), while two `iperf3` clients run for the window: UDP at a percentage of the framed 600-byte line rate (19,592 pps) and a TCP flow capped at 5 Mbit/s (2 Mbit/s for the worst case). Port counters are sampled every 10 s over the serial console and the table is read back every 60 s. If the OpenFlow session drops, the harness waits for the redial, restores every rule installed so far and continues, recording the outage.

### 4.3 Blackout probe

`blackout` pings the receiver every 10 ms from the workload node for 16 s, flushes at +5 s, and reports the longest gap between replies. Modes: no flush (control), full wipe and reinstall, selective delete of the quarantine rules. Depths 0 and 126; idle and 1,000 pps UDP; 3 repetitions.

### 4.4 Reproduction of the first benchmark

The first benchmark's three conditions (0, 32 and 126 installed rules, requested 128), four tests (TCP, UDP at MTU, UDP at 64 B, idle), 10 s windows. The rerun used 5 trials per cell and a 2 s gap between trials; the first run had 3 to 4 valid trials per cell.

### 4.5 Saturating sweep (superseded)

`sweep` visited 12 depths with four tests each at saturating offered load, and 16 layout variants. It completed one round of the depth conditions. With saturating loads the switch dropped its session in 23 of 55 trials, and the failures cascaded into invalid trials, so its numbers are not used; the ladders replaced it.

### 4.6 Inference runs

`/api/generate` on each Ollama instance (non-streaming, 300 tokens, six fixed prompts), two requests in flight per model, 600 s, both models at once. Calibration at 1, 2 and 4 in flight (45 s each) chose the level.

### 5.4 Drop-hit ladders (inconclusive)

Three ladders (`hitfirst`, `hitmiddle`, `hitlast`) offered a paced UDP stream whose source address matched a DROP rule at the first, middle or last table position (depths 32 and 126). After a bug fix (the first validation matched the Pi's real address instead of the alias the flood is sent from), traffic was dropped (Port 2 TX near 0) but the hit rule's packet counter stayed at 0, and the OpenFlow session was lost in five of the seven final hit-ladder steps, 7 to 30 s into the step, at only 500 pps. The earlier smoke test at 4 rules counted hits (62,355 in 10 s), so the counter does work in a small table. These runs are not interpreted.

## 7. Harness defects found and fixed

Each defect was in the harness or driver, not the switch, unless noted. Chronological.

| # | Found in | Defect | Effect | Fix |
| --- | --- | --- | --- | --- |
| 1 | Smoke workday | The `iperf3` receiver probe ran before forwarding rules existed (empty table is default-drop) | Probe hung, run aborted | Probe moved after the table reset |
| 2 | Smoke workday | A switch-initiated session loss aborted the run | Run lost | Wait for redial, restore all rules, record the outage |
| 3 | Smoke workday | Built-in OpenFlow heartbeat is about 15 s apart | CPU stalls invisible | 1 Hz echo probe and per-echo latency events |
| 4 | Smoke ladder | Loss check only looked inside the step window | A loss 1.6 s after the step was missed | Post-step control-plane settle watch (20 s) |
| 5 | Smoke ladder | A killed client left the receiver busy | Next step invalid | 6 s pause after a loss; one retry on "server busy" |
| 6 | Driver 1 | Driver never checked the bridge state; its logged exit code was always 0 (command substitution reset `$?`) | All steps failed fast and were recorded as done (incident A) | Pre-step bridge check, real exit codes, mask the bridge during runs |
| 7 | Sweep | Installs were not guarded against a session in HANDSHAKE | Sweep aborted after 25 min | Every install, flush and restore wrapped in a retry that restarts on a session change |
| 8 | Workday | Table restore sent the rules once, then polled an empty table for 30 s after a second session loss | Run aborted | Session-epoch counter; any change restarts the install |
| 9 | Workday | The receiver stayed "busy" for minutes after a killed client | Three runs skipped | One-shot `iperf3` servers with a 10 s idle timeout; retry on "busy" and "connection refused" |
| 10 | Workday | An unbounded TCP flow saturates the switch by itself | Collapse of TCP and repeated session loss at 25% UDP load | TCP rate cap (`--tcp-mbps`) |
| 11 | Workday | A session loss at a window edge made the end-of-window table check fatal | Two runs aborted | Recorded as an observation; the next flush rebuilds from nothing |
| 12 | Workday | The periodic table check was unguarded | One run aborted on a readback timeout | Failure recorded, run continues |
| 13 | Hit ladder | The hit rule used the workload's real address | Hit-ladder results meaningless | Rule uses the alias address of the flood |
| 14 | Workday | Table verification bounded by poll count, not time (each poll can wait 10 s) | One run silent for 12.5 min | Wall-clock deadline of about 75 s per attempt, retried up to 6 times |
| 15 | Switch | Network stack wedged after overload (management address unreachable, serial alive) | Needed a power cycle (incident C) | Not a harness defect; operator action |

## 8. Artifact format

Artifacts are JSON with 64-bit integers written as `{"$bigint": "..."}` (Council Invariant 2). All carry a `provenance` block:

- `schema` (`zodiac-depth-bench/v1` for ladder, workday, blackout and sweep; `zodiac-dataplane-bench/v1` for the three-depth run) and `origin: "physical_bench_run"` (artifacts without it are refused by the renderers).
- `command`, `startedAtIso`, `startedMonotonicNs`, `finishedMonotonicNs` (the run span is their difference).
- `controllerHost`, `switchIdentity` (DPID, firmware 0.86, CPU UID, OpenFlow peer, serial path), `workload` (SSH target, interface, address, kernel, `iperf3` version), `iperfServer`.
- `tool` (`scriptSha256`, `gitCommit`, `gitDirty`) and `flowTableVerified`.

Body fields by command: `ladder` has `steps[]` (`depth`, `offeredPps`, `trial` with `metrics` and raw `show ports` text, `sessionLost`, `stopped`, `recoveryNs`, `echoRecoveryNs`); `workday` has `windows[]` (`samples[]` of 10 s counter deltas, `verifications[]`, `sessionLosses[]`, per-flow `iperf3` interval bytes and end totals); `blackout` has `records[]` (ping gap and flush timings); all have `sessionEvents[]` (`connected`, `ready`, `disconnected`, `deadPeerTimeout`, `echoLatency`, `silence`, each with a monotonic timestamp).

Counters come from the switch's serial `show ports` and, for cross-check, the workload NIC's sysfs counters. Rates are derived with integer arithmetic. The analysis scripts convert to floating point for presentation only.

## 9. Reproducing

```bash

# Jetson, with zodiac-bridge.service stopped, iperf3 receivers running on the Mac (ports 5201 and 5202)

npm run build:server
npm run bench:dataplane -- plan                       # matrix and time estimates, no hardware touched
npm run bench:dataplane -- preflight --server 10.0.2.119 --pi-ssh agent@10.0.0.45 --pi-ip 10.0.2.50 --tap-iface enx9c69d39dd0a6
npm run bench:dataplane -- ladder  --server 10.0.2.119 --pi-ssh agent@10.0.0.45 --pi-ip 10.0.2.50 --layout base
npm run bench:dataplane -- ladder  --server 10.0.2.119 --pi-ssh agent@10.0.0.45 --pi-ip 10.0.2.50 --payload 64 --step-seconds 30 --rates-pps 1000,2000,4000,8000,12000,16000,20000,24000,28000
npm run bench:dataplane -- workday --server 10.0.2.119 --pi-ssh agent@10.0.0.45 --pi-ip 10.0.2.50 --profile typical --udp-load-percent 25 --tcp-mbps 5
npm run bench:dataplane -- blackout --server 10.0.2.119 --pi-ssh agent@10.0.0.45 --pi-ip 10.0.2.50

# Analysis (any machine)

python3 docs/benchmarks/analysis/analyze_depth.py docs/benchmarks/results/ladder-2026-10-04 docs/benchmarks/results/full-2026-10-04
python3 docs/benchmarks/analysis/build_timeline.py --status docs/benchmarks/analysis/run-status-2026-10-04.json docs/benchmarks/results/rerun-2026-10-04 docs/benchmarks/results/smoke-2026-10-04 docs/benchmarks/results/ladder-2026-10-04 docs/benchmarks/results/full-2026-10-04
```

Run these only on the isolated bench: they wipe the switch's flow table and saturate the Port 2 path, and the production bridge must be stopped so the benchmark is the switch's only controller. `iperf3` receivers: `iperf3 -s -1 -B 10.0.2.119 -p 5201 --idle-timeout 10` (and 5202), restarted in a loop.

## 10. Known gaps

The drop-path capacity is unmeasured (section 5.4); the switch CPU is not measured directly; the unexplained session losses are not root-caused (8 in the three complete working-window hours); typical-50% produced one usable window; layout ladders other than `base` and `fwdfirst` are single rounds. These are repeated with their implications in the whitepaper, section 6.
