# On-wire conformance run of the evaluation's rule sets (RQ4), 2026-10-31

The run pre-registered in `docs/research/evaluation-plan.md` section 16 (registered by commit `6ac2da1` before any wire data; amendments A1 to A4 in 16.10), on the real Zodiac FX through the bridge's guarded experiment endpoint. Every number below is generated by `scripts/wire-report.ts` from the sessions' `results.json` (in `campaign/` and `repeats/`); nothing is typed in. **Admissible means the verifier accepts a rule set. This run asks whether the switch does what the verifier's model and the intent say, for the flows chosen.** It is physical-capture evidence: O2 (the Zodiac P3 link) and O3 (a mirror of the P2 link) on the Jetson, and a promiscuous capture on `rpi-hailo`'s workload NIC for what leaves port 1; raw captures with SHA-256 are in each set's directory.

## What was run

- **The bundle:** 132 rule sets over the eight intents (`bundle-2026-10-31/`, seed 20261031, `index.json` SHA-256 `4bb9a7bdf27d503eacc2bd4c0f0d32bab24d1d93b4b2db191de940b68f7fa7dc`): per intent the reference, every surviving mutant a chosen flow can tell from the reference, up to 8 recorded model-proposed sets (round-robin over the models), and 4 equivalence controls. `flows.json` SHA-256 starts `0d122ba0c7d11d24`, `coverage-flows.json` `f12aa353c91d99cc`.
- **Two measures per flow:** M1, whether the ports where a frame was observed equal the ports the verifier's own match function predicts; M2, whether the observation satisfies the intent's own clause for that packet (a missing delivery is charged only on ports the testbed can observe).
- **Which sets ran:** 128 of the bundle's 132. tap-return-isolation has no separating flows, so its own session was not run and its 4 equivalence controls were not installed; its reference ran in the smoke and coverage sessions (the other seven intents ran all of their sets, references included).
- **Sessions:** a smoke gate on the 8 references (port 1 flows); a coverage session on the 8 references with one flow per intent clause in both entry directions, port 1 and port 2; one session per intent over its other sets (port 1 flows); then the three repeat sessions of 16.5 (20 separable sets drawn by the seed). tap-return-isolation has no separating flows, so it appears only through its reference.
- **How frames were sent:** every frame entering port 1 is a raw frame from `agentic-node-01`'s workload NIC (`eth0`) with the flow's exact header fields; every frame entering port 2 is a raw frame from the same node's USB NIC (`eth1`), which the owner moved onto the isolated uplink VLAN of the NETGEAR uplink switch for the run (that segment then holds only that node and the Zodiac's P2 link). Frames entering port 3 were not sent (decision 8: the capture NICs stay receive-only).
- **Unattended:** the owner gave unilateral permission for all sessions of this run on 2026-10-31 and left; the runner's stop rules replaced the owner's presence, and none fired. The rule sets of the bundle were approved by the SHA-256 of `index.json`, enforced in code.

## What the numbers say, and no more

- **No disagreement with the model and no violation of the intent in any flow sent.** All sessions agree on every flow, including the 70 coverage flows of the references that enter port 2. The "All" row counts set-runs and flow checks, not distinct sets or flows: the 8 references run in three sessions (smoke, coverage and their own intent session), so the 128 distinct sets that ran are 143 set-runs. An all-agree result has an interval; it is evidence about these flows, not a proof about the switch.
- **The uplink side was checked for the references.** For INTENT-7 (uplink-arp-confinement) the reference's coverage flows show ARP from the allowed peers 10.0.2.1 and 10.0.2.254 reaching port 1, ARP from a non-peer address dropped, and a default-deny IPv4 frame dropped. This is a check of the intent and of the A10 uplink confinement on those flows, with an isolated uplink segment and forged raw frames from node-01. It does not show how real uplink traffic behaves.
- **The repeats are stable.** The same 20 sets in three sessions were observed identically on every flow, so ordering and timing effects did not show on these flows.
- **The model's equivalence claims held where tested:** the 4 equivalence controls of each of the seven intents that ran their sessions (sets no flow can tell from the reference) behaved like the reference on the flows run, which tests only that the switch agrees with the model's equivalence.

## A finding about the switch path (F1, carried from the validation runs)

IPv4 frames whose source and destination address are identical are **not forwarded** (nothing on O2 or O3) while the model predicts forwarding; observed from three different hosts in a diagnostic and in the first smoke runs (`../validation-2026-10-31/`). The direction is safe; where the drop happens (sender NIC, lab-side switch or Zodiac) is not established. Such frames are excluded from the candidate flows (amendment A3), so this run neither contains nor contradicts them.

## Other observations

- The bridge's periodic isolation re-check reports `mismatch` (with the experiment table installed) for up to about two minutes after each session, then returns to `verified` on its own; the experiment endpoint's own restore reports were accurate throughout (`restore.json` in every set's directory). After the last session the status read `verified` with 0 mismatches and the table-miss dropping.
- Two harness defects were found and fixed before this run (non-promiscuous capture; flat evidence directory); see `../validation-2026-10-31/`.

## What this run does not show

- **Exhaustive behaviour:** only the flows chosen (3 to 7 separating flows per intent, plus clause-coverage flows on the references). Fields the model does not track (L4 ports, VLAN) are not distinguished at all.
- **Most surviving mutants cannot be told from their reference by any sendable flow** (4 to 9 of each intent's 6 to 18 survivors are separable); the controls and the inseparable survivors test only equivalence.
- **Frames arriving from the tap (port 3)** are untested, and so is the clause that concerns them, for every intent.
- **The uplink side for sets other than the references:** non-reference sets were run on port 1 flows only, because every intent fixes port 2 behaviour exactly, so all admissible sets behave alike there.
- **Real uplink traffic, other switches or firmware** (0.86 is the ledger value and was not re-read by this run), and any property of the model-proposed sets beyond what the verifier admitted: an admissible set is correct for its intent only as far as the intent and the verifier are.
- **Whether the proposals are good:** this tests the verifier's model against hardware, not the proposers.
