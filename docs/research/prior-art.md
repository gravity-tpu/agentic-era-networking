# Supporting Research & Prior Art

This document compiles the academic literature that establishes the theoretical and empirical foundations of **Zodiac**. It situates the project within network verification, switch micro-benchmarking, active data-plane testing, and LLM-assisted configuration synthesis, and defines exactly where Zodiac contributes a new result.

## 2. Surveyed Literature

### Lineage A: LLM-Driven Network Configuration and Synthesis

Recent work explores using generative models to produce router configurations, translations, and management scripts:

1. **Mondal et al., "What do LLMs need to Synthesize Correct Router Configurations?" (ACM HotNets 2023)**  
   *Authors:* Rajdeep Mondal, Alan Tang, Ryan Beckett, Todd Millstein, George Varghese.  
   *Core Finding:* LLMs (GPT-4) in isolation frequently generate syntactically plausible but semantically disastrous network configurations, hallucinating topology and violating invariants. The authors propose *Verified Prompt Programming*, pairing the LLM with Batfish to provide localized verifier feedback, yielding a 6x–10x reduction in human prompts.  
   *Relation to Zodiac:* Directly informs Zodiac's proposer/verifier architecture. However, Mondal et al. evaluate only router configuration languages (Cisco/Juniper) against software simulators (Batfish) without hardware constraints, data-plane latency models, or physical packet-level testing.

2. **Wang et al., "NetConfEval: Can LLMs Generate Correct Network Configurations?" (ACM CoNEXT 2024)**  
   *Authors:* Changjie Wang, Mariano Scazzariello, Alireza Farshin, Simone Ferlin, Dejan Kostić, Marco Chiesa.  
   *Core Finding:* NetConfEval introduces a standardized benchmark for evaluating LLMs on network configuration synthesis across diverse protocols (BGP, OSPF, VLANs). Demonstrates that configuration accuracy drops sharply as topological complexity increases.  
   *Relation to Zodiac:* Provides a template for structuring reproducible intent-to-policy evaluation benchmarks. Zodiac complements NetConfEval by evaluating OpenFlow flow-mod rules rather than static device syntax, and testing them on physical silicon rather than synthetic test harnesses.

3. **Mani et al., "Enhancing Network Management Using Code Generated by Large Language Models" (ACM HotNets 2023)**  
   *Authors:* Sathiya Kumaran Mani, Yajie Zhou, Kevin Hsieh, Santiago Segarra, Trevor Eberl, Eliran Azulai, Ido Frizler, Ranveer Chandra, Srikanth Kandula.  
   *Core Finding:* Demonstrates that generating verifiable intermediate code (e.g. Python network scripts) is significantly more reliable than asking LLMs to directly manipulate raw topologies, mitigating hallucination and scale barriers.  
   *Relation to Zodiac:* Supports Zodiac's architectural invariant: agents must emit structured, typed representations (`FlowModOptions`) rather than unconstrained imperative configurations.

### Lineage B: Switch Hardware Characterization and Empirical Bottlenecks

Empirical studies demonstrate that physical OpenFlow switches deviate sharply from textbook models:

1. **Rotsos et al., "OFLOPS: An Open Framework for OpenFlow Switch Evaluation" (PAM 2012)**  
   *Authors:* Charalampos Rotsos, Nadi Sarrar, Steve Uhlig, Rob Sherwood, Andrew W. Moore.  
   *Core Finding:* Introduces hardware instrumentation to measure OpenFlow switch bottlenecks. Proves that flow-mod insertion latency, rule modification times, and packet processing overhead vary wildly across implementations and firmware versions, frequently bottlenecked by the embedded CPU rather than switching silicon.  
   *Relation to Zodiac:* Zodiac's benchmark harness (`scripts/zodiac-dataplane-bench.ts`) follows the OFLOPS methodology, uncovering the Zodiac FX's 58 µs + 4.24 µs/rule software flow evaluation constraint.

2. **Kuźniar et al., "What You Need to Know About SDN Flow Tables" (PAM 2015)**  
   *Authors:* Maciej Kuźniar, Peter Perešíni, Dejan Kostić.  
   *Core Finding:* Measures commercial OpenFlow switches and exposes critical discrepancies between the specification and hardware reality: non-linear rule installation delays, table overflow degradation, and premature `OFPT_BARRIER_REPLY` messages sent before rules are actually active in the forwarding plane.  
   *Relation to Zodiac:* Directly motivates Zodiac's Track B and Invariant 4: control-plane handshake confirmations are insufficient. The verifier must account for table limits (128 rules), and readback must verify physical data-plane state.

3. **Lazaris et al., "Tango: Simplifying SDN Control with Automatic Switch Property Inference" (ACM CoNEXT 2014)**  
   *Authors:* Aggelos Lazaris, Daniel Tahara, Xin Huang, et al.  
   *Core Finding:* Demonstrates that SDN controllers must infer switch-specific hardware properties (table capacity, supported match combinations, rule installation delay) to make safe forwarding decisions.  
   *Relation to Zodiac:* Zodiac implements Tango's core philosophy directly within verification: hardware limits (CPU forwarding cost, table budget) are formal inputs to the policy verifier (`verifyPlanAdmissible` and roadmap A8).

### Lineage C: Active Data-Plane Testing and Conformance

Bridging control-plane models and physical forwarding behavior:

1. **Perešíni et al., "Monocle: Dynamic, Fine-Grained Data Plane Monitoring" (ACM CoNEXT 2015)**  
   *Authors:* Peter Perešíni, Maciej Kuźniar, Dejan Kostić.  
   *Core Finding:* Uses Boolean satisfiability (SAT) to generate probe packets that exercise individual rules in hardware switches, verifying whether the actual forwarding plane matches controller expectations during live operation.  
   *Relation to Zodiac:* Informs Zodiac's Track B Conformance Probe. While Monocle probes arbitrary switches dynamically, Zodiac leverages packet-class partitioning (`enumeratePacketClasses` in `src/sdn/intent-spec.ts`) to verify complete table coverage.

2. **Zeng et al., "Automatic Test Packet Generation" (ACM CoNEXT 2012)**  
   *Authors:* Hongyi Zeng, Peyman Kazemian, George Varghese, Nick McKeown.  
   *Core Finding:* Introduces ATPG, algorithmically generating a minimal set of test packets to achieve full rule and link coverage across a network topology based on geometric models from Header Space Analysis.  
   *Relation to Zodiac:* Inspires the test packet generation mechanism used by Zodiac's conformance engine to validate firmware rule enforcement on the wire.

3. **Kuźniar et al., "A SOFT Way for OpenFlow Switch Interoperability Testing" (ACM CoNEXT 2012)**  
   *Authors:* Maciej Kuźniar, Peter Perešíni, Marco Canini, Daniele Venzano, Dejan Kostić.  
   *Core Finding:* Identifies OpenFlow specification ambiguities and implementation bugs by running differential testing between software switches (OVS) and hardware targets.  
   *Relation to Zodiac:* Justifies Zodiac's dual-target architecture: running an independent userspace Open vSwitch instance (`br-sim` on port 6634) on the Jetson to cross-check the abstract evaluator against standard reference OpenFlow behavior.

### Lineage D: Formal Network Verification and Invariant Checking

Foundational algorithms for checking reachability, isolation, and loop-freedom:

 1. **Kazemian et al., "Header Space Analysis: Static Checking for Networks" (USENIX NSDI 2012)**  
    *Authors:* Peyman Kazemian, George Varghese, Nick McKeown.  
    *Core Finding:* Treats packet headers as points in a geometric $\{0, 1\}^L$ space and network devices as transformation functions, enabling static proof of isolation and reachability.

 2. **Khurshid et al., "VeriFlow: Verifying Network-Wide Invariants in Real Time" (USENIX NSDI 2013)**  
    *Authors:* Ahmed Khurshid, Xuan Zou, Wenxuan Zhou, Matthew Caesar, P. Brighten Godfrey.  
    *Core Finding:* Introduces real-time, microsecond-scale invariant verification by partitioning header space into equivalence classes (Equivalence Classes / ECs) and building incremental forwarding graphs upon every rule update.

 3. **Kazemian et al., "Real Time Network Policy Checking using NetPlumber" (USENIX NSDI 2013)**  
    *Authors:* Peyman Kazemian, Michael Chang, Hongyi Zeng, George Varghese, Nick McKeown, Scott Whyte.  
    *Core Finding:* Extends Header Space Analysis to incremental online checking via dependency graphs between rules, enabling sub-millisecond policy compliance validation.

 4. **Mai et al., "Debugging the Data Plane with Anteater" (ACM SIGCOMM 2011)**  
    *Authors:* Haohui Mai, Ahmed Khurshid, Rachit Agarwal, Matthew Caesar, P. Brighten Godfrey, Samuel T. King.  
    *Core Finding:* Encodes forwarding tables and network invariants into SAT formulas, using boolean solvers to detect data-plane bugs and unreachable rules.

 5. **Fogel et al., "A General Approach to Network Configuration Analysis" (USENIX NSDI 2015)**  
    *Authors:* Ari Fogel, Stanley Fung, Luis Pedrosa, Meg Walraed-Sullivan, Ramesh Govindan, Ratul Mahajan, Todd Millstein.  
    *Core Finding:* Batfish derives data-plane models directly from multi-vendor router configurations, enabling proactive verification before configurations touch production networks.

## 3. The Gap: Where Zodiac Fits

Existing research occupies three separate quadrants:

| Dimension | Formal Verifiers (HSA, Batfish) | Switch Benchmarks (OFLOPS, PAM '15) | LLM Synthesis (HotNets '23, NetConfEval) | **Zodiac Testbed** |
| :--- | :--- | :--- | :--- | :--- |
| **Input** | Human configs | Synthetic rule sets | Natural language intents | **Agent/Human Intent** |
| **Evaluation Model** | Abstract mathematical | Empirical measurement | Software simulation / Batfish | **Deterministic Verifier + Hardware Cost Model** |
| **Execution Target** | None (Static) | Physical hardware | Simulated topology | **Physical Silicon (Zodiac FX + Jetson + RPi)** |
| **Bottleneck Addressed** | Logical misconfiguration | Device micro-architecture | Prompting / Syntax errors | **MCU Overload, Table Limits & Wire Leaks** |
| **Adversarial Validation** | None | Benchmarking loads | None | **Live Hardware Red Team (Pi 3B+ / Pi 5)** |
| **Data Provenance** | Synthetic | Lab measurements | Synthetic benchmarks | **Cryptographic & Monotonic Invariant 6** |

### The Zodiac Pitch

1. **Simulators assume infinite, frictionless silicon.** Batfish and Header Space Analysis verify whether an abstract policy allows packet $P$ to reach port $Q$. They do not know that placing 120 forwarding rules before a drop rule imposes an extra 500 µs of software lookup latency on an embedded MCU, or that an offered rate of $1.3\times$ capacity drops the control plane entirely.
2. **Generative models synthesize code without consequences.** LLM research shows models generate promising initial drafts with subtle structural errors. In software, a compiler rejects them; in cloud deployments, an emulator allows them. In constrained hardware, a flawed policy causes session resets and table wipes.
3. **Zodiac closes the loop on physical silicon.** Zodiac pairs natural-language policy generation with:
   - A **deterministic property verifier** (checking isolation, hairpins, shadowing, prerequisites, and intent compliance);
   - A **measured hardware cost model** (rejecting rule sets that exceed table or MCU capacity);
   - A **human approval gate**;
   - An **on-wire conformance probe** reading ground truth from physical mirror taps;
   - A **live adversary** exercising edge cases against the installed policy.

Zodiac transforms agentic network policy from speculative simulation into grounded, reproducible systems research.
